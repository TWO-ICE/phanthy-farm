# 微信支付SDK曝高危漏洞：陌陌、vivo已中招，白帽子直接“踢门”曝光

2018年7月3日中午12点47分，腾讯云的代码仓库里悄悄发生了一次提交。

又过了14分钟——其实已经是第二天上午8点09分——仓库里又迎来了一次更新。如果你不是盯着代码行数看的开发者，这两次普通的提交根本不会引起注意。但这短短两天内的两次修改背后，藏着一场足以让无数电商商家冷汗直流的安全危机。

就在这两天，国外安全社区突然抛出了一枚“重磅炸弹”：微信支付官方的JAVA版本SDK存在严重漏洞。

这不是那种需要极高权限才能触发的“鸡肋”漏洞，而是直接位于核心支付逻辑中的致命伤。攻击者利用这个漏洞，不仅能绕过支付验证——说白了就是“买东西不花钱”——还能把商家的服务器当自家后花园，进进出出，窃取数据。

更让人后背发凉的是，发布漏洞的白帽子并没有按常规流程“先通知厂商，等修复后再公开”。他把漏洞细节和攻击方式一股脑全晒到了网上。那一刻，所有使用微信支付JAVA SDK的商家，实际上都在“裸奔”。

陌陌、vivo，这些名字只是第一批被确认的受害者。

**一场针对支付核心的“降维打击”**

咱们把技术术语先抛开，看这事儿到底有多严重。

这次出问题的是微信支付的SDK（软件开发工具包）。对于商家来说，这是接微信支付的“转接头”。用户在手机上点付款，微信发个消息给商家的服务器说“这人付钱了”，商家服务器收到消息，通过SDK验证一下，然后发货。

白帽汇安全研究院发现的问题就出在这个验证环节。

漏洞的学名听起来很吓人，叫XML外部实体注入（XXE）。通俗点说，就是SDK在处理XML格式的数据时，太“轻信”别人了。XML协议里有个功能叫“外部实体”，允许你在读文件的时候，去加载外面的东西。

正常开发者用这个功能是为了方便，比如读个配置文件。但坏人要是用起来，这就是个合法的“后门”。

攻击者只需要给商家的通知URL（就是微信告诉商家“支付成功”的那个接口）发一段精心构造的数据。这段数据里藏着恶意指令，告诉服务器：“嘿，别光处理支付，顺便去读一下我指定的文件，或者帮我扫一下内网有没有没关的端口。”

服务器呢？它老实巴交地照做了。

这可不是危言耸听。白帽汇安全研究院已经拿到了确凿的证据。他们用BurpSuite（一种常用的抓包工具）做了个简单测试，构造了一个Payload发过去。结果呢？商家服务器乖乖地向攻击者的远程服务器发起了请求。

这一来一回，攻击者就拿到了通往内网的“门票”。

**从“逃单”到“提权”，一步之遥**

如果说读取文件只是“偷窥”，那接下来的操作就是“打劫”。

一旦攻击者能通过这个漏洞控制了商家的服务器，他们最想要什么？当然不是你的几张高清壁纸，而是你的密钥。

在支付系统里，有个关键的安全密钥，比如md5-key和merchant-Id（商户ID）。这就跟你家保险柜的钥匙一样。只要拿到这串字符，攻击者就能伪造支付成功的通知。

你要是卖手机的，攻击者发一条“支付成功”的消息过来，你的系统以为是微信发的，货就发出去了。钱？没收着。

这叫绕过支付。对商家来说，这是实打实的真金白银的损失。

但这还不是最坏的。既然都能读取服务器文件了，为什么不更进一步？在某些系统配置下，XXE漏洞甚至可以执行系统命令。这意味着攻击者可以直接在服务器上装个后门，或者把服务器变成“肉鸡”，去攻击别人。

白帽汇那边给出的复现视频里，服务器像个提线木偶一样，按照攻击者的指令把数据传了过去。画面很安静，但只要看懂那张截图，任何一个运维人员都会立刻从椅子上跳起来。

**官方的“两连补”与白帽子的“先斩后奏”**

这事儿最戏剧性的是时间线。

根据白帽汇的追踪，微信官方在漏洞被公开前后，动作其实挺快。

2018年7月3日12点47分，也就是漏洞发酵刚开始的时候，微信修改了SDK代码。这次修复主要针对的就是XXE漏洞。

到了第二天，7月4日8点09分，官方又补了一刀。这次是修复一个可能导致DoS（拒绝服务）攻击的漏洞。DoS虽然不如XXE那么“致命”，但它能让服务器直接瘫痪，商家一秒钟都别想做生意。

官方确实在干活，而且是在连续加班修Bug。

问题在于，在漏洞被公开的那个时间点——2018年7月3日下午16点之前，官方并没有发布任何预警，也没有发布补丁。那段时间是一个可怕的“真空期”。

更让厂商头疼的是那位“泄密者”——发布漏洞的白帽子。

按照行规，发现了这种高危漏洞，通常是先私下通知厂商（这叫“负责任的漏洞披露”），给厂商留出修复的时间（通常是30到90天）。等厂商修好了，或者过了期限还不动，再公开细节，这叫保护用户。

这次不一样。这位白帽子直接掀了桌子。

他没等微信修好，也没等微信发公告，直接把漏洞怎么用、代码怎么写、危害有多大，全发到了国外安全社区。

甚至还留下了语言“彩蛋”。白帽汇研究院的人发现，这位老兄发布的内容里混着中文标点符号。大伙儿都在猜，这搞不好是位国内的高手，可能是因为沟通不畅，或者是单纯的一时热血，搞了个“零日（0-day）直接公开”。

不管动机如何，结果很残酷：攻击者们和防守者们几乎同时看到了漏洞代码。在那一刻，想搞破坏的人比想修补的人占了先机。

**历史总是惊人的相似：PHP版本的前车之鉴**

如果你翻翻微信支付SDK的老黄历，会发现这次JAVA版本出事，其实是有预兆的。

早在以前，PHP版本的SDK就出现过同样的漏洞。

那时候闹得也是沸沸扬扬。后来官方修好了，大家以为这事儿过去了。谁知道，到了JAVA版本上，坑还在。这就像是你家一楼窗户破了，你补好了；搬到二楼的时候，发现二楼窗户又破了，还是原来那个洞。

这次公开的漏洞信息里，明确提到了`WXPayUtil.xmlToMap`这个方法。这是微信支付JAVA SDK里的一个核心工具类，专门用来把XML消息转换成Map格式。

只要你的代码里调用了这个方法，并且没有手动把“禁止外部实体”的开关打开，你就中招了。

不需要什么复杂的黑客技巧，只要你会写代码，会发请求，就能利用。

**给商户的一份“避灾”指南**

现在的情况是：陌陌、vivo已经确认“湿鞋”了。

微信支付被用得这么广，电商、游戏、O2O，哪个行业不用？理论上，所有用了JAVA SDK且没有及时更新代码的商户，都在风险名单上。

白帽汇那边的建议很直接，别等了，自查吧。

怎么自查？看你的代码版本。

如果你还在用老版本的SDK，赶紧去微信官方的Git仓库或者Maven仓库看一眼。对比一下那两个关键的时间点：7月3日中午和7月4日上午。如果你的代码还没包含那两次修复，说明你是“裸奔”状态。

如果你是技术人员，修复办法其实很简单，但也容易被忽略。

Java里处理XML的类叫`DocumentBuilderFactory`。这个类有个默认的“坑”，就是允许解析外部实体。你需要显式地把它关掉。

代码其实就两行：

```java
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setExpandEntityReferences(false);
```

这行代码的意思很直白：别给我瞎读外面的东西，只处理我给你的字符串。

补上这两行代码，重新打包上线，这个“后门”也就堵上了。

**写在最后**

写到这里，必须得说一句老生常谈的话：安全是个基本功，但也最容易变成“表面功夫”。

对于微信官方来说，SDK是给千千万万开发者用的“地基”。地基里的钢筋（代码逻辑）如果生锈了，盖在上面的楼（商家的业务）越高就越危险。这次漏洞的出现，说明官方在代码审计和自动化的安全检测上，依然有改进的空间。

而对于我们这些开发者、商户来说，这也敲响了警钟。

不要盲目信任第三方的SDK，哪怕它来自腾讯，来自阿里，或者来自全球最大的开源社区。代码是人写的，人就会犯错。

这次的漏洞之所以影响巨大，是因为它直接击中了“钱袋子”。支付安全，不仅是技术问题，更是生存问题。

那位白帽子究竟是谁，我们可能永远不知道。他留下的中文标点符号，成了安全圈里一个短暂的谈资。但对我们来说，更现实的行动是：

检查服务器日志，看看有没有被攻击的痕迹；
检查代码版本，看看是不是最新的；
检查那个`xmlToMap`方法，看看有没有加上安全补丁。

毕竟，在这个攻防对抗的世界里，漏洞公开的那一刻，比赛就已经开始了。而你，必须站在起跑线上。
